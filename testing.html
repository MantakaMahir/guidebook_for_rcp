Trace 10 · Testing

Code you cannot see failing is code that will.

RCP is verified at four levels: TypeScript's type checker, fast unit tests, integration tests against a real Oracle database, and a pure-SQL harness that tests the schema itself. Each level catches a different class of mistake, and each one runs from a single command.

Level 0: the compiler is a test suite

Before anything executes, npm run typecheck runs tsc --noEmit. Because TypeScript types flow from interfaces like SessionUser down through every function, a misspelled column name in a mapping or a forgotten field fails the build: not the user. In a codebase where SQL rows become objects, the type system is the first line of tests.

In Java terms

Running tsc --noEmit is compiling without producing class files: javac as a verification step. The difference is that TypeScript's types also describe the shapes of database rows and JSON payloads, so "it compiles" already means "the layers agree on the data".

Unit tests: node:test, no framework

Node ships a test runner; RCP uses it directly with the strict assertion module. Here is the complete test file for password hashing: small enough to hold in your head, which is the point:

What makes these tests good:

  • They test behavior, not implementation. "A different password is rejected" stays true however scrypt is wrapped; a test that checked internal variable names would break on every refactor.
  • They include the hostile cases. Malformed hash strings, extra segments: the inputs an attacker would poke, asserted to return false rather than throw.
  • They run in milliseconds with zero setup. npm test executes every unit test using nothing but Node: no database, no network.

Integration tests: the real database answers

Unit tests prove the functions are correct in isolation; integration tests prove they are correct against Oracle: that the SQL parses, the constraints accept what should be accepted, and the triggers fire. Five workflows live in tests/integration/:

FileWhat it exercises
database-health.test.tsPool connects, schema exists, seed counts match
auth-flow.test.tsRegister → login → session → logout against real tables
profile-workflow.test.tsProfile updates, privacy visibility
publication-workflow.test.tsPublication creation, stewardship, DOI import path
collaboration-workflow.test.tsPosts, applications, connections, notifications

They are deliberately gated: set RUN_ORACLE_INTEGRATION_TESTS=1 to run them, otherwise they skip. Tests that require external infrastructure must never fail a build just because the database is unreachable: and must never be skipped silently when you asked for them.

The SQL harness: testing the database with SQL

The schema gets its own test suite, written in the language of the thing being tested. database/05_database_tests.sql runs as the owner account after a rebuild and asserts the invariants of the schema itself: constraint behavior, the exact number of grants issued to RCP_APP, sequence integrity: printing PASS/FAIL blocks through DBMS_OUTPUT. It replays 00_reset → 01_schema → 02_seed_data → 06_enhanced_er_migration → 03_views_and_plsql → 04_security → 05_database_tests against local Oracle XE. If any script errors, WHENEVER SQLERROR EXIT stops the run cold: the same fail-fast discipline as the unit tests, at the DDL level.

In Java terms

The four levels are your familiar pyramid with a database twist: types ≈ compile checks, unit tests ≈ JUnit, integration tests ≈ tests against a real container, and the SQL harness ≈ contract tests for the persistence layer written by the persistence layer itself.

What to copy when you add code

  • Pure logic (validation, normalization, matching rules) → a unit test in tests/unit/, run by npm test.
  • Anything touching a table → an integration workflow step, run gated behind the environment flag.
  • Schema changes → update the numbered scripts and the assertions in 05_database_tests.sql in the same change.
  • Before any review: npm run typecheck, npm test, npm run build: the three commands the project treats as the definition of "done".
