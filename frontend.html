Trace 03 · Frontend

A page is an async function that returns HTML.

We follow /researchers: the public directory of researchers. One folder, one function, one SQL query, one rendered page. No controller, no template engine, no fetch glue: the page function queries the database itself and returns markup.

The folder is the route

The URL /researchers exists because this file exists. Delete the file and the URL stops resolving; rename the folder and the URL moves. Routing is the filesystem.

  • export default async function: the framework calls this function on every request and sends whatever it returns to the browser.
  • searchParams: the query string (?q=vision&sort=name) arrives as an object. URL parameters are just function arguments.
  • Promise.all([first, second, third]): run three queries concurrently instead of sequentially. Like starting three threads and joining them, written as one expression.
  • @/server/search: the @/ alias means src/, so this imports src/server/search.ts. A server module, called directly, no HTTP hop needed.

In Java terms

This one function is controller + service call + view. searchResearchers() is the service method; the returned <main> element is the rendered JSP equivalent: except it is type-checked at compile time, and a typo in a column name fails the build instead of the user.

JSX: markup written inside the function

The second half of the same file returns the HTML. The angle-bracket syntax is JSX: HTML embedded in TypeScript. Curly braces { } drop expressions into the markup, and .map() is the loop construct: one list item per row.

Read the three patterns that do most of the work in this codebase:

  • {expression}: interpolate a value. {researcher.FULL_NAME} prints the column.
  • {list.map(item => <Card key={item.id} />)}: loop. The key= prop gives each item a stable identity, like a primary key for the renderer.
  • {condition && <jsx>}: conditional render. If the left side is false, nothing is emitted. The empty state on the last line uses exactly this.

Note className instead of class: class is a reserved word in TypeScript, so JSX renamed the attribute. Styling itself is plain CSS: one global stylesheet, src/app/globals.css, no CSS-in-JS machinery.

Server components: the page ran before you saw it

Here is the part with no Java equivalent. The function above executed on the server: it awaited real Oracle queries, and the browser received finished HTML. This is a server component: the default kind. Its powers and its limits:

  • It may await database calls directly: that is how the page got its data without any API round trip.
  • It may not listen to clicks or hold state. It runs once per request, like a template being rendered, not like a live object.

Breakpoint

The researchers array never traveled to the browser as data: only the rendered HTML did. The database rows, the query, and the column names stay on the server. This is the golden rule from Trace 01, working exactly as designed.

Client components: where clicks live

Interactivity needs code that runs in the browser. A file opts in with 'use client' at the top; from then on it ships to the browser and can hold state and handle events. The login form is the cleanest example in the codebase:

  • useState(''): a field that survives re-renders. Reading it gives the current value; calling the setter re-renders the component. Think of it as an instance variable that repaints the UI when written.
  • onSubmit={submit}: attaching a handler is just passing a function reference, like a Java listener.
  • fetch('/api/auth/login', { method: 'POST', body }): the client side of the boundary from Trace 02: the browser calls the server over HTTP, sending JSON, and inspects the status code before trusting the body.

In Java terms

Server component ≈ code that runs in main() on the server at request time. Client component ≈ a Swing/JavaFX panel shipped to the user's machine: it keeps state, reacts to events, and talks back to the server over the network when it needs something it cannot compute itself.
