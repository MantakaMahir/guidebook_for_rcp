Trace 09 · A feature end to end

Research posts: draft, publish, close, notify.

Everything you have traced so far meets in one feature. A researcher posts a collaboration opportunity; others apply; the owner closes it and every applicant is notified. This trace walks the server module that owns the whole lifecycle: src/server/posts.ts.

Creating a post: one transaction, several tables

A post is not one row: it is a RESEARCH_POST row plus any number of required areas and required skills in two junction tables. All of it commits together:

You should recognize every part by now: validation before SQL, sequence for the ID, RETURNING INTO to carry the new ID into the junction inserts, withTransaction making the bundle atomic. New posts start in status 'DRAFT': invisible to everyone but the owner.

The requirements step also shows defensive SQL: each chosen area is inserted with INSERT ... SELECT ... FROM RESEARCH_AREA WHERE area_id = :areaId AND status = 'ACTIVE', so an area that was deactivated (or never existed) simply produces no row: and a pre-check counts matches and fails the whole request if any ID was bogus.

Ownership: check the row under lock

Publishing, editing, and closing all begin with the same two questions: does the post exist, and do you own it? Answered under a row lock:

FOR UPDATE locks the selected row until the transaction ends. If two requests try to change the same post at once, the second waits for the first to commit or roll back before it proceeds: the database serializes them for you.

In Java terms

SELECT ... FOR UPDATE is synchronized on a database row: a mutex held inside the transaction. The check-then-act pattern (read owner, then update) is only safe because the lock spans both steps.

State machine: DRAFT → OPEN → CLOSED

A post's status column has legal transitions, and the code enforces them explicitly. Publishing re-validates the business rules one last time:

A post may only go public if it has at least one requirement and a deadline in the future. The same module's updatePost and closePost guard their own transitions: a CLOSED post can never reopen, a DEACTIVATED post can never change. Illegal transitions throw INVALID_TRANSITION and the row is untouched.

Closing: side effects inside the same transaction

When a post closes, every applicant with a live application must hear about it. The notifications are written in the very same transaction as the status change: a closed post with unsent notifications cannot happen:

insertNotification receives the open connection on purpose: it writes into the same transaction rather than opening its own. Notifications are also recipient-owned: a user's notification feed queries only rows where they are the recipient, enforced server-side.

The other big flow: OpenAlex import

The same discipline scales up for the platform's integration feature, importing publications from the OpenAlex catalog by DOI:

  • Provider calls stay on the server. src/server/integrations/openalex.ts fetches DOI metadata; the optional API key never leaves the server process.
  • Preview before commit. The client sends DOI strings and receives a classified preview: matching, new, or excluded: without writing anything.
  • Atomic batches. On confirmation the server re-fetches the selected records and inserts each batch (capped at 25 works) in one transaction: publication rows, ordered authors, area links, citation snapshot, and an EXTERNAL_PUBLICATION_SOURCE provenance row recording where the data came from. All of it commits together or not at all.

Pattern to remember

Every write feature in this codebase has the same skeleton: validate → authorize → lock/read → mutate inside withTransaction → return fresh state. When you build the next feature, copy the skeleton.
