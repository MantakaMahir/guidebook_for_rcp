Trace 01 · The fundamentals

A website is two programs talking.

You already write programs. The web is just a particular shape of program: one side waits, the other side asks. This guide traces the Research Collaboration Platform through eleven layers of that conversation: from the browser on your laptop down to the Oracle tables: using the real code of the real system.

  • FRAME 0 · BROWSERThe client

    Your laptop. Renders HTML, applies CSS, runs JavaScript, sends HTTP requests.

  • FRAME 1 · NEXT.JSThe server

    A Node.js program. Maps URLs to functions, renders pages, answers API calls.

  • FRAME 2 · DRIVERnode-oracledb

    A library of pooled connections that carries SQL to the database and rows back.

  • FRAME 3 · ORACLEThe database

    Tables, constraints, triggers, views. The only place anything is remembered.

A request is a function call over a socket

When you open https://rcp-research.vercel.app/researchers, your browser opens a TCP connection and writes a carefully formatted text message. In C terms it is connect() + write(); in Java terms, writing to a Socket output stream. The message looks exactly like this on the wire:

The first line carries everything that matters: the method (GET: read something), the path (/researchers: which resource), and the query string (?q=vision: arguments, like passing parameters to a function). The rest are headers: metadata about the request.

The response is a return value with a status code

The server answers with its own text message. The first line is a status code: think of it as the return value of the call, where 0 meant success but 404 meant "no such function":

200OKSuccess, here is the result
201CreatedSuccess, and a new record exists now
400Bad RequestIllegalArgumentException

Three languages, three jobs

The HTML the server returns is not a program: it is a data structure, closer to a serialized object than to code. The browser turns it into three things:

  • HTML: structure. The fields of the object: headings, forms, links.
  • CSS: presentation. Rules that say how each part looks, like formatting specifiers applied after the fact.
  • JavaScript: behavior. The only actual program of the three; it runs inside your browser.

In Java terms

HTML is the struct, CSS is toString() formatting, JavaScript is the methods. A page without JS is a read-only dump; a page with JS is a live object you can interact with.

The split that organizes everything: client vs server

Some code runs in the browser (client-side) and some runs on the machine that owns the domain (server-side). The same JavaScript language runs on both sides: what differs is what each side is allowed to touch. This is the single most important idea in this guide:

Breakpoint: the golden rule of RCP

The browser never connects to Oracle. Every database query runs on the server, inside src/server/. The browser only ever talks to the server over HTTP. Credentials, passwords, and API keys live on the server side of that line and are physically unreachable from client code.

Your vocabulary, translated

RCP is written in TypeScript: JavaScript with a static type system. If you know Java, you already know 80% of the syntax: types on variables, functions, classes, import. The runtime is Node.js, which runs TypeScript outside a browser. Here is the translation table this guide will keep using:

You know (Java / C++)Here it is (RCP)
public static void mainA request handler: export async function POST(request)
Servlet / controllerNext.js API route files under src/app/api/
JDBC connection pool (DataSource)oracledb.createPool(config) in db-core.ts
PreparedStatement with ? placeholdersSQL with named binds: :email, :tokenHash
interface / structTypeScript interface in src/types/domain.ts
#include / importimport: same idea, module paths instead of headers
JUnit assertionsnode:test + node:assert/strict
setAutoCommit(false), commit, rollbackwithTransaction(callback) in db-core.ts
Thread waiting on I/Oawait: the runtime parks the function until the result arrives

In Java terms

async/await is the web's answer to blocking I/O without a thread per request. await db.execute(sql) reads like a blocking JDBC call, but underneath the runtime suspends the function and serves other requests meanwhile. Read await as "this line needs the result before continuing": the concurrency is the runtime's problem, not yours.
