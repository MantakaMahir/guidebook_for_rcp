TRACE 05 / 11 · the driver

Trace 05 · Node ↔ Oracle

One small file carries every query to the database.

src/server/db-core.ts is 124 lines and it is the only place in the application that knows Oracle exists. Everything else: posts, profiles, imports: calls three exports from this file. If you understand this trace, you understand how the whole platform persists data.

The library: oracledb is JDBC for Node

The oracledb npm package is Oracle's official driver for Node.js. Same mental model as JDBC: you open connections, execute SQL with binds, fetch rows, commit. The driver even has the same two modes: Thin (pure JavaScript) and Thick (native client libraries), and RCP runs Thick mode against Oracle Client.

Line 1, import 'server-only', is the fence from Trace 02: if any browser code ever imports this file, the build fails. Line 7 sets the default row shape: each row comes back as a JavaScript object keyed by column name ({ FULL_NAME: 'Ada Lovelace' }) instead of an array.

A pool, not a connection

Opening a database connection is slow: network handshake, authentication, session setup. A web server handling dozens of requests per second cannot afford one per request, so it keeps a pool: a small set of open connections that get borrowed and returned. Exactly what a JDBC DataSource pool does.

  • Credentials come from environment variables: ORACLE_USER, ORACLE_PASSWORD, ORACLE_CONNECT_STRING. They exist in the server process's memory, never in the code, never in the browser. requiredEnv throws if one is missing, so a misconfigured server fails fast at startup instead of failing mysteriously at query time.
  • poolMax: 4: at most four simultaneous connections. The pool is deliberately small for the current app and cloud database. When all four are busy, callers wait up to queueTimeout (10 seconds) for one to free up.
  • stmtCacheSize: 30: parsed statements are cached so repeated queries skip the parse step. JDBC statement caching, same idea.
  • The pool promise lives on globalThis so that in development, when modules get reloaded, the old pool is reused instead of leaked.

The wallet block (configDir, walletPassword) is how the app proves its identity to the cloud database: a folder of certificates and configuration instead of a plain password-over-the-wire. Trace 11 unpacks it.

query(): borrow, execute with binds, return

This is the read path used across the codebase: one function, and every call site gets the same discipline for free:

Three habits this function enforces:

  • Borrow and return. connection() borrows from the pool; the finally block guarantees the connection goes back even when the query throws. Leak a connection and the pool starves: the web equivalent of forgetting to close a file handle.
  • SQL and values travel separately. The SQL text with :placeholders goes one way, the values go in the binds object. The database compiles the statement first and treats the values purely as data, so no input can change the query's meaning.
  • LOBs are read before returning. Oracle CLOB columns stream; readLob drains each one into a plain string so callers never see driver internals.

In Java terms

query(sql, { email })
is PreparedStatement ps = conn.prepareStatement(sql); ps.setString(1, email); ps.executeQuery();: with the placeholder named :email instead of positional ?, and try-with-resources handling the close.

Breakpoint: SQL injection dies here

Because every query in RCP goes through binds, a user typing ' OR 1=1 -- into a search box just becomes a strange literal string that matches nothing. Injection requires string-concatenated SQL, and this codebase never builds SQL by concatenation.

withTransaction(): commit on success, rollback on throw

Writes need atomicity. The pattern in RCP: pass a function that receives a connection; if it returns, commit; if it throws, rollback; either way, close.

In Java terms

This is conn.setAutoCommit(false) + try/catch with commit()/rollback(), packaged as a higher-order function. The caller writes only the work; the transaction ceremony exists once, here. Registration used it in Trace 04: two INSERTs, one atomic unit.

Where IDs come from: RCP_ID_SEQ

Oracle 11g has no auto-increment columns, so the schema defines one sequence for the whole database, and every INSERT draws the next ID from it:

You saw it in action in Trace 04: VALUES (RCP_ID_SEQ.NEXTVAL, :email, :passwordHash, :role, 'ACTIVE', :fullName). Each .NEXTVAL atomically returns a fresh number that no other session will ever receive: concurrency-safe ID generation built into the engine.

In Java terms

A sequence is a thread-safe counter owned by the database itself: AtomicLong, except it survives restarts, works across every connection at once, and never hands the same number to two transactions.
