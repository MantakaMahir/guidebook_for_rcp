Trace 08 · Security

Follow a password from keystroke to database.

Security in RCP is not a feature: it is the shape of the code. This trace follows a password from the moment it is typed, shows how a login session is carried without ever exposing the token's secret, and lists the defenses that make whole classes of attacks structurally impossible.

Hashing: the password never exists twice

The instant registration validates, the plaintext password is transformed into an scrypt hash and discarded. Only the hash is stored:

  • scrypt is a key-derivation function deliberately expensive in CPU and memory: computing one hash is fast enough for a login, but trying billions of guesses is economically ruinous for an attacker.
  • The salt is 16 random bytes, unique per password, stored next to the hash. Identical passwords produce different hashes, so precomputed rainbow tables are useless.
  • The stored format scrypt$salt$key is self-describing: the verification function parses it, re-derives with the stored salt, and compares.

Two details that separate professional code from tutorial code:

  • timingSafeEqual compares in constant time. A normal === returns early on the first differing byte, leaking: via microseconds: how much of the hash matched. Constant-time comparison leaks nothing.
  • Every malformed input returns false, never throws. An attacker poking the format gets one uniform answer.

In Java terms

Think of scrypt as a one-way function with a per-input random nonce: hash(password, salt) is cheap to verify if you know the password, and hopeless to invert if you don't. Storing plaintext: even "encrypted" plaintext you can decrypt: fails the moment the database leaks. Only a one-way hash survives that day.

Login: uniform failure, then a hashed token

Verification alone has a subtle leak: if the server answers faster for "email not found" than for "wrong password", an attacker can enumerate which emails exist. RCP's login defeats that by always running the hash check: against a dummy hash when the account does not exist:

No account, blocked account, or wrong password all fall into the same INVALID_CREDENTIALS path after the same amount of work. On success, a session begins:

  • randomBytes(32).toString('base64url'): 256 bits of fresh randomness become the session token. Unforgeable because unguessable.
  • Only SHA-256(token) is written to USER_SESSION: the token itself lives solely in the user's browser cookie.

The cookie: HttpOnly is the moat

  • httpOnly: true: JavaScript in the browser cannot read this cookie. A successful cross-site-scripting bug still cannot steal the session token.
  • sameSite: 'strict': the browser refuses to attach the cookie to requests arriving from other sites, which neutralizes CSRF-style session riding.
  • secure in production: the cookie only travels over HTTPS.

Every subsequent request carries the cookie; the server resolves it with one query that checks all four conditions at once: token matches, not revoked, not expired, account still active:

Logout is the mirror image: UPDATE USER_SESSION SET revoked_at = SYSTIMESTAMP WHERE token_hash = :tokenHash. Sessions are data, so revocation is a row update: no server restarts, no in-memory registries.

Injection: closed by construction

SQL injection needs user input concatenated into SQL text. RCP removes the ingredient instead of guarding the recipe:

  • Every query uses named binds: you saw query(sql, binds) in Trace 05; there is no other path to the database in the codebase.
  • Ordering comes from an allow-list. A sort parameter cannot be bound like a value (SQL binds do not substitute column names), so the search module maps the incoming string onto a fixed server-side list of legal ORDER BY fragments. Anything unrecognized falls back to the default.
  • The database agrees. Even the dynamic import logic builds only bind placeholders: never column or table names: from input.

Breakpoint

When you add a query to this codebase, the rule is absolute: values go through :binds, structure goes through allow-lists. A single concatenated query re-opens a door the whole architecture is built to keep shut.
