Trace 07 · Views & triggers

The database runs code too.

So far every trace ended at an INSERT. This one continues past it: Oracle fires triggers, fills subtype tables, and refuses illegal mutations: all inside the statement you already sent. The database in this project is an active participant, not a passive filing cabinet.

BEFORE INSERT: deriving a column you never sent

RESEARCHER_PROFILE carries a column academic_type: STUDENT or FACULTY. The application never supplies it. A BEFORE INSERT trigger computes it from the role that was supplied, using a mapping table:

  • BEFORE INSERT ... FOR EACH ROW: the body runs once per inserted row, before the row is written. It can still change the row.
  • :NEW.column: the row being inserted. Reading :NEW.role, writing :NEW.academic_type := ... is editing the incoming data in place.
  • SELECT ... INTO variable: PL/SQL's way of fetching one value into a local variable. %TYPE declares the variable with the same type as the referenced column, so they can never drift apart.
  • EXCEPTION WHEN NO_DATA_FOUND: if the mapping table has no entry for the role, the lookup raises; the handler converts it into a clean application error with RAISE_APPLICATION_ERROR. The INSERT dies with message ORA-20059.

In Java terms

A trigger is an observer hooked into the storage engine itself: except it runs inside the same transaction, can mutate the value being saved, and cannot be unregistered by forgetting a line of app code.

AFTER INSERT: a profile row gets its subtype row

Immediately after the profile row lands, a second trigger maintains the specialization tables: the enhanced-ER part of the model, where STUDENT and FACULTY are subtypes with their own attributes:

So the registration transaction you traced in Trace 04 writes the profile and session rows from application code, plus the subtype row created here by Oracle: all inside one transaction. The subtype tables pin their identity with constraints worth reading closely:

The CHECK constraint freezes academic_type to 'STUDENT' in this table, and the foreign key references the parent on both columns: so a student row can only ever attach to a profile whose derived type is also STUDENT. A researcher cannot be both subtypes and cannot be the wrong subtype: that is the ER specialization rule, enforced mechanically.

Guard triggers: some mutations are simply illegal

Because academic_type is derived, letting anyone UPDATE it would corrupt the model. A guard trigger makes the column read-only after insert, and re-checks it whenever role changes:

:OLD is the row before the update, :NEW the row after; comparing them is how a trigger detects what actually changed. The second guard says: you may not promote a STUDENT profile into a FACULTY role by UPDATE, because the subtype rows would no longer match. The system forces a deliberate migration instead of a silent one.

Views: named queries as stable interfaces

A view stores a SELECT and lets you query it like a table. RCP uses them to hand the application pre-joined, pre-filtered results: the open-posts directory, for instance, is one view:

Three reasons this exists as a view instead of being inlined in application code:

  • One definition of "open post." Status OPEN and a future deadline, decided once, used everywhere.
  • The JOIN lives where the schema lives. If the tables change, the view is fixed in one place.
  • Least privilege. The runtime user can be granted SELECT on views without holding SELECT on every underlying table.

Packages: procedures with a namespace

For logic with several cooperating procedures, PL/SQL groups them into a package: a spec (the interface) plus a body (the implementation). The contribution reconciler keeps derived publication data consistent:

  • The spec is the contract callers see; the body can change without breaking them. Splitting interface from implementation, Java-interface style.
  • AUTHID DEFINER means the procedure runs with the privileges of its owner (RCP_OWNER), not the caller (RCP_APP): a controlled privilege escalation, used so the runtime user can trigger maintenance logic it is not allowed to run directly.
  • Call it from SQL as RCP_CONTRIBUTION_SYNC.reconcile_publication(:id): the package name is the namespace.

In Java terms

Package spec ≈ interface, package body ≈ the implementing class, AUTHID DEFINER ≈ a method running under a different security principal. The database has had all three since before most frameworks existed.

The full chain, one registration

Putting Traces 04-07 together, registering the researcher "Ayesha Rahman" does all of this:

  1. POST /api/auth/register validates and hashes (Trace 04).
  2. withTransaction borrows a pooled connection (Trace 05).
  3. INSERT into RESEARCHER_PROFILE: TRG_PROFILE_ACADEMIC_TYPE_BI derives academic_type from the role.
  4. TRG_PROFILE_SUBTYPE_DEFAULT inserts the matching STUDENT_RESEARCHER or FACULTY_RESEARCHER row.
  5. INSERT into USER_SESSION with the hashed token.
  6. Commit: all rows land together, or none do.

One HTTP request, one transaction, several database objects cooperating. That is the whole platform in miniature.
