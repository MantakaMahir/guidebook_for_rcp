Trace 02 · The architecture

One repo, three layers, one rule.

Before reading any code, hold the whole shape in your head. RCP is a single repository whose folders map one-to-one onto layers of a stack. Once you know which folder you are in, you already know what the code is allowed to do.

  • FRAME 0 · src/appPages & routes

    Every URL is a file here. Pages render HTML; api/ routes answer JSON.

  • FRAME 1 · src/serverBusiness logic

    Validation, authorization, and the SQL that talks to Oracle. Server-only.

  • FRAME 2 · src/typesShared contracts

    TypeScript interfaces describing every row and payload.

  • FRAME 3 · database/Oracle DDL

    Numbered SQL scripts: schema, seeds, views, security, tests.

The folder map is the architecture

Open the repository root. Each top-level folder is one concern, and the dependency arrows only ever point downward: pages call server modules, server modules call the database layer, and nothing points back up:

In Java terms

src/app is your controllers and views, src/server is the service layer, src/types is the DTO package, and database/ is your migration scripts. The difference: there is no separate "view template" language: React components return HTML directly, so the controller and the view live in one function.

Two kinds of file inside src/app

Next.js, the framework RCP uses, treats a file named page.tsx as a page and a file named route.ts as an API endpoint. That naming convention is the routing table: there is no separate routes file to maintain.

File on diskURL it servesWhat it returns
src/app/(public)/researchers/page.tsx/researchersHTML page
src/app/dashboard/page.tsx/dashboardHTML page (needs login)
src/app/api/auth/login/route.tsPOST /api/auth/loginJSON
src/app/api/posts/route.tsGET/POST /api/postsJSON

The parentheses in (public) and (auth) are route groups: they organize files without appearing in the URL. So (public)/researchers/page.tsx serves /researchers, not /public/researchers.

Breakpoint

Everything under src/app/api/ and everything under src/server/ runs only on the server. Any file that begins with import 'server-only' will refuse to compile into browser code: a hard fence the toolchain enforces for you.

The one rule that keeps it safe

Draw a vertical line between the browser and the server. Client code may call server code over HTTP. Server code may call Oracle. Client code may never reach Oracle, and Oracle credentials never cross the line.

This is why src/server/db-core.ts: the file that holds the Oracle connection: is the most important file in the repository, and why the next traces keep returning to it.

In C terms

Think of the boundary as a privilege ring. The browser is user mode; the server is kernel mode; the database is the hardware. User mode gets hardware access only by making a syscall (an HTTP request) that the kernel validates first.
