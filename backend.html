Trace 04 · Backend

An API route is one exported function per HTTP method.

Trace the registration request end to end: the form in the browser POSTs JSON to /api/auth/register, a single file receives it, guards it, validates it, writes the profile and session rows in one transaction, and lets Oracle triggers maintain the subtype row before answering with a cookie and a status code.

The receiving function

The file src/app/api/auth/register/route.ts exists, so the endpoint POST /api/auth/register exists. The framework calls whichever exported function matches the HTTP method: GET, POST, PUT, PATCH, DELETE. This file exports POST:

The whole file is 34 lines. Read it as a pipeline of guards followed by one real action:

  • Origin guard: reject cross-site form posts before anything else runs.
  • Rate limit: at most 5 attempts per minute per IP and per email address. Registration is expensive and abusable, so it is throttled twice.
  • Size guard: refuse bodies larger than the limit, so a giant payload cannot waste server memory.
  • Parse: await request.json() deserializes the body. Invalid JSON is a 400, never a crash.
  • Act: registerAccount(input) does the real work (next step), then the session cookie is set and 201 Created goes back with the new user as JSON.

In Java terms

This is a servlet's doPost() written as one exported function. return Response.json(body, options) is response.getWriter().write(body) plus setStatus(status) in one expression. Early return instead of nested if is the same guard-clause style you would use anywhere.

The real work: validate, hash, insert: one transaction

The route file contains no SQL. That lives one layer down in src/server/auth.ts, where registerAccount validates the input, hashes the password, and explicitly writes the profile plus session rows atomically. The profile INSERT also fires the subtype trigger covered in Trace 07:

Four ideas packed into those lines:

  • Validate first. validateRegistration throws AuthError on bad email, short password, or unknown role: before anything touches the database.
  • Never store the password. Only hashPassword()'s output is inserted. Trace 08 dissects it.
  • Named binds. :email, :passwordHash are placeholders filled from the object argument: the same protection as a PreparedStatement. No string concatenation into SQL, anywhere in this codebase.
  • RETURNING ... INTO. Oracle hands back the generated researcher_id in the same round trip, so the second INSERT can reference it without a follow-up query.

Breakpoint: atomicity

Both INSERTs run inside withTransaction. If the session insert fails, the profile insert is rolled back: you can never end up with a researcher who has no session row mid-registration. Either both rows commit or neither exists. Trace 05 shows how withTransaction is built.

Errors are status codes, not stack traces

The end of the route maps exceptions onto safe responses. The client gets a stable error code and a human message; internal details never leave the server:

HTTP methodCRUD meaningExamples in RCP
GETRead/api/researchers, /api/posts, /api/notifications
POSTCreate/api/auth/register, /api/posts, /api/connections
PATCHPartial update / state change/api/posts/:id, /api/publications/:id, /api/applications/:id/status, /api/admin/users/:id/status
DELETEDeactivate / remove/api/publications/:id deactivates a publication record

The URL names the resource; the method names the verb. PATCH /api/applications/42/status reads as a sentence: "partially update the status of application 42".
