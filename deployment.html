Trace 11 · Deployment

From your laptop to the cloud, same code.

The final trace: how the application boots on a developer machine, how it proves its identity to a cloud Oracle database with a wallet of certificates, and how it ends up serving the world from Vercel. Nothing changes between environments except configuration: which is exactly the point.

Running it locally

The server reads its configuration from environment files that Git ignores (.env.local for the app, .env.oracle.local for owner-account database scripts). Secrets live in those files, never in code:

VariablePurpose
ORACLE_USERRuntime database user: RCP_APP, the least-privilege account
ORACLE_PASSWORDIts password
ORACLE_CONNECT_STRINGWhich database service to dial, e.g. rcpdb_tp
ORACLE_SCHEMASchema set on each connection: RCP_OWNER
TNS_ADMINDirectory holding the extracted cloud wallet
ORACLE_WALLET_PASSWORDUnlocks the wallet's private key
ORACLE_CLIENT_LIB_DIROracle Client libraries for Thick mode
SESSION_SECRETServer-side secret for session handling

Breakpoint

Environment files are in .gitignore for a reason. A password committed to a public repository is a leaked password forever: Git never forgets. The wallet folder is treated the same way.

The wallet: certificates instead of a bare password

The production database is an Oracle Autonomous Database in Oracle Cloud. Connecting to it uses mTLS: both sides prove identity with certificates. The "wallet" is a zip of those certificates plus tnsnames.ora (an address book mapping service names like rcpdb_tp to hosts) and sqlnet.ora (TLS configuration). TNS_ADMIN tells the driver where that folder lives.

The driver itself runs in Thick mode: it loads native Oracle Client libraries from ORACLE_CLIENT_LIB_DIR before opening any connection. That one-time initialization lives in db-core.ts, guarded so it runs exactly once per process:

The double guard (a done flag and a pending promise) makes the initialization safe under concurrency: even if ten requests race the first pool creation, the client initializes once and everyone else awaits the same promise.

In Java terms

This is the classic double-checked initialization of a shared resource: volatile flag plus in-flight future: written with async. The pattern exists because native-library init is neither repeatable nor thread-safe, so exactly one caller may ever run it.

Serverless: when there is no writable disk

On Vercel, the platform that hosts RCP in production, a function instance cannot rely on a wallet folder existing at a known path. The solution ships the wallet inside the configuration: the wallet's files are base64-encoded into one environment variable, and the first connection writes them into a temp directory:

Two environments, one code path: laptops use TNS_ADMIN pointing at the extracted wallet; Vercel sets WALLET_BASE64 and the function materializes the wallet on first use: rewriting sqlnet.ora's internal DIRECTORY reference so the certificates resolve in their new home. This is why the live site can reach the cloud database without any persistent filesystem.

The production topology

  • EDGE · VERCELNext.js on Vercel

    Builds the app, serves pages, runs API routes. Deploys from the GitHub main branch.

  • CLOUD · OCIAutonomous DB RCPDB

    Oracle 19c, Always Free tier, Singapore region. Runtime user RCP_APP, schema RCP_OWNER.

  • EXTERNALOpenAlex API

    Public research catalog. Called server-side only, for DOI imports.

A push to main triggers a Vercel build; when the build passes, the new version replaces the old one at rcp-research.vercel.app. Schema changes are not part of that pipeline: they are applied deliberately by running the numbered SQL scripts as the owner account, exactly as Trace 06 described.

Every one of these errors was hit and solved during this project's development: the table is scar tissue, documented so you spend minutes where the original author spent hours.
